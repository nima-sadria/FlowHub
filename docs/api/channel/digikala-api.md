# مستند فنی API فروشندگان دیجی‌کالا

راهنمای فارسی اتصال به DK Marketplace Open API برای مدیریت کالا، تنوع، قیمت، موجودی، سفارش، بسته و رخدادهای فروشندگان.

> این راهنما از مشخصات رسمی OpenAPI دیجی‌کالا تهیه شده است. جزئیات هر مسیر، فیلدها و سطح دسترسی را همیشه در مرجع رسمی کنترل کنید؛ این API در زمان نگارش ۲۴۶ مسیر اعلام می‌کند.

## ۱ — پیش‌نیازها و نشانی پایه

برای استفاده از API باید یک **Active Client** در دیجی‌کالا ثبت و برای آن سطح دسترسی‌های لازم (Scope) فعال شده باشد. ابتدا Scopeهای مورد نیاز برنامه را مشخص کنید، سپس فرایند تأیید دسترسی فروشنده را کامل کنید.

نشانی پایهٔ محیط عملیاتی:

`baseUrl = https://seller.digikala.com/open-api/v1`

تمام درخواست‌ها باید با HTTPS و بدنهٔ JSON، در صورت وجود بدنه، ارسال شوند.

## ۲ — دریافت و نوسازی توکن

پس از تأیید دسترسی برنامه توسط فروشنده، دیجی‌کالا کاربر را همراه با `authorization_code` به برنامه برمی‌گرداند. این کد را برای ساخت توکن به مسیر زیر بفرستید:

```http
POST /auth/token
Content-Type: application/json

{
  "authorization_code": "CODE_FROM_CALLBACK"
}
```

پاسخ موفق شامل `access_token`، `refresh_token` و زمان انقضای هر دو است. توکن دسترسی را کوتاه‌عمر در نظر بگیرید و زمان انقضا را از پاسخ سرویس بخوانید؛ مقدار ثابت یا فرضی برای آن نگذارید.

برای نوسازی توکن منقضی‌شده:

```http
POST /auth/refresh-token
Content-Type: application/json

{
  "access_token": "EXPIRED_ACCESS_TOKEN",
  "refresh_token": "CURRENT_REFRESH_TOKEN"
}
```

در پاسخ نوسازی، هر دو توکن جدید را جایگزین مقادیر قبلی کنید. در پایان اتصال یا هنگام قطع دسترسی، از `POST /auth/revoke` استفاده کنید.

## ۳ — احراز هویت و Scope

مشخصات رسمی API از Bearer Token با قالب JWT استفاده می‌کند. در همهٔ مسیرهای محافظت‌شده، توکن را در هدر `Authorization` بفرستید:

```shell
curl 'https://seller.digikala.com/open-api/v1/orders' \
  -H 'Authorization: Bearer ACCESS_TOKEN' \
  -H 'Content-Type: application/json'
```

هر مسیر به Scope مشخصی وابسته است. برای نمونه، مسیرهای کالا Scope `product`، مسیرهای سفارش Scope مربوط به سفارش و مسیرهای وب‌هوک Scope وب‌هوک می‌خواهند. دسترسی `read` برای خواندن و `write` برای عملیات تغییر لازم است؛ وجود یک Scope در فهرست کلی به معنی فعال‌بودن آن برای Client شما نیست.

مسیرهای کمکی احراز هویت:

| مسیر | کاربرد |
| --- | --- |
| `GET /auth/scopes` | فهرست Scopeهای تعریف‌شده در سرویس |
| `GET /auth/scopes/{client_code}` | Scopeهای قابل‌استفادهٔ Client |
| `POST /auth/token` | ساخت Access Token و Refresh Token |
| `POST /auth/refresh-token` | دریافت توکن‌های تازه |
| `POST /auth/revoke` | لغو توکن و دسترسی برنامه |

## ۴ — الگوی پاسخ و صفحه‌بندی

پاسخ‌های موفق معمولاً یک شیء با وضعیت و داده بازمی‌گردانند. در پاسخ‌های فهرستی، اطلاعات صفحه‌بندی در `data.pager` وجود دارد.

```json
{
  "status": "ok",
  "data": {
    "pager": {
      "page": 1,
      "item_per_page": 50,
      "total_pages": 4,
      "total_rows": 183
    },
    "items": []
  }
}
```

پارامترهای صفحه‌بندی در هر مسیر یکسان نیستند، اما `page` و `size` یا `item_per_page` الگوهای رایج‌اند. پارامترهای مجاز همان مسیر را از Swagger بررسی کنید و تا زمانی که `page` از `total_pages` عبور نکرده، دریافت داده را ادامه دهید.

| فیلد | کاربرد |
| --- | --- |
| `pager.page` | شمارهٔ صفحهٔ فعلی |
| `pager.item_per_page` | تعداد آیتم‌های هر صفحه |
| `pager.total_pages` | تعداد کل صفحه‌ها |
| `pager.total_rows` | تعداد کل آیتم‌ها |
| `items` | داده‌های همان صفحه |

## ۵ — گروه‌های اصلی API

مستند رسمی طیف بزرگی از عملیات فروشنده را پوشش می‌دهد. این‌ها مهم‌ترین گروه‌ها برای یکپارچه‌سازی کانال فروش هستند:

| حوزه | مسیرهای نمونه | کاربرد |
| --- | --- | --- |
| کالا و دسته‌بندی | `GET /categories/tree`، `GET /products/seller` | یافتن دسته، کالای فروشنده و وضعیت انتشار |
| ایجاد کالا | `/product-creation/*`، `/draft-products/*` | جست‌وجو، پیش‌نویس، بارگذاری تصویر و ثبت/انتشار کالا |
| تنوع و قیمت | `/variants/*` | ایجاد و ویرایش تنوع، قیمت فروش، فعال‌سازی و موجودی فروشنده |
| سفارش | `GET /orders`، `GET /orders/{order_item_id}` | دریافت فهرست سفارش، جزئیات، تاریخچه و آمار |
| موجودی | `/inventories/*` | مشاهده، به‌روزرسانی و خروجی‌گرفتن از موجودی |
| بسته و ارسال | `/packages/*`، `/shipments/*` | ساخت بسته، ظرفیت انبار و پیگیری ارسال |
| پروموشن | `/promotions/*`، `/lightening-deal/*` | کمپین‌ها، تخفیف هوشمند و پیشنهاد شگفت‌انگیز |
| وب‌هوک | `/webhook/*` | مدیریت اعلان رویدادها در مقصد شما |

## ۶ — همگام‌سازی کالا، تنوع و موجودی

برای همگام‌سازی پایدار، ابتدا شناسه‌های دیجی‌کالا را در کنار شناسه‌های داخلی FlowHub نگه دارید. در این API، مسیرهای کالا، تنوع و موجودی از هم جدا هستند؛ پس قبل از تغییر قیمت یا موجودی، تطابق شناسهٔ محصول/تنوع را اعتبارسنجی کنید.

نمونهٔ واکشی موجودی یک تنوع:

```http
GET /inventories/{product_variant_id}
Authorization: Bearer ACCESS_TOKEN
```

عملیات نوشتن را صف‌بندی کنید، پاسخ هر درخواست را ذخیره کنید و برای خطاهای گذرا سیاست تلاش مجدد با backoff داشته باشید. بدون بررسی وضعیت نهایی، تغییر را در سیستم داخلی قطعی تلقی نکنید.

## ۷ — سفارش، بسته و ارسال

برای دریافت سفارش‌ها از `GET /orders` شروع کنید و برای هر آیتم، جزئیات را از `GET /orders/{order_item_id}` بخوانید. سپس، متناسب با مدل ارسال فروشنده، اطلاعات بسته، انبار و ارسال را از گروه‌های `packages` و `shipments` مدیریت کنید.

قبل از ایجاد یا ویرایش بسته، ظرفیت و قیود انبار را از مسیرهای مربوط به `packages/warehouses` بررسی کنید. شناسه‌های سفارش، آیتم سفارش، بسته و ارسال را جداگانه نگهدارید؛ این شناسه‌ها لزوماً قابل‌جایگزینی با هم نیستند.

## ۸ — وب‌هوک‌ها

وب‌هوک برای دریافت رویدادها بدون polling مناسب است. مسیرهای گروه `Webhook` را برای ثبت، مشاهده، ویرایش یا حذف مقصد اعلان بررسی کنید. مقصد باید HTTPS، پایدار و قادر به پاسخ سریع 2xx باشد.

- بدنهٔ رخداد را پیش از پردازش در صف پایدار ذخیره کنید.
- رویدادها را با یک شناسهٔ یکتا idempotent پردازش کنید.
- برای رخدادهای تکراری یا نامرتب، پردازش قابل‌تکرار و واکشی وضعیت نهایی از API داشته باشید.
- رازها و توکن‌ها را فقط در مخزن امن نگه دارید و در لاگ ثبت نکنید.

## ۹ — خطاها و محدودیت درخواست

خطاها معمولاً شامل `status`، `message` و `code` هستند. برای خطاهای اعتبارسنجی، شیء `errors` نیز فیلدهای مشکل‌دار را برمی‌گرداند.

| وضعیت | معنی و اقدام پیشنهادی |
| --- | --- |
| `400` | ورودی یا بدنه نامعتبر؛ فیلدهای `errors` را اصلاح کنید. |
| `401` | توکن نامعتبر یا منقضی؛ یک‌بار نوسازی توکن را امتحان کنید. |
| `403` | Scope کافی نیست؛ دسترسی Client را از پنل/پشتیبانی پیگیری کنید. |
| `404` | منبع یا شناسه پیدا نشد؛ نگاشت شناسه‌ها را کنترل کنید. |
| `429` | محدودیت درخواست؛ زمان اعلام‌شده را رعایت و با backoff تلاش کنید. |
| `500` | خطای سرویس؛ درخواست idempotent را با backoff دوباره امتحان کنید. |

## ۱۰ — چک‌لیست پیاده‌سازی

- Scope حداقلی لازم را برای هر قابلیت درخواست کنید.
- Access Token و Refresh Token را رمزگذاری‌شده نگه دارید و پس از نوسازی، هر دو را جایگزین کنید.
- صفحه‌بندی، محدودیت درخواست و خطاهای 401/429/5xx را در کلاینت پوشش دهید.
- مبلغ‌ها، زمان‌ها و شناسه‌ها را دقیقاً طبق schema همان endpoint پردازش کنید.
- برای عملیات نوشتن، لاگ قابل‌ردیابی، صف و کنترل تکراری‌بودن درخواست داشته باشید.
